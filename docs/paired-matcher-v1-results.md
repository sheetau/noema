# 原文と定義の同時符号化による概念照合

原文と候補定義を二列入力として固定MiniLMへ渡し、対象範囲と定義の対応を共通ヘッドで判定する処理を実装した。新規資料では、選択した方式の正解数が日英とも14/20で、既存3係数方式の13/20から各1件増えた。一方、日英とも正しい組は13/20から11/20へ減った。改善と悪化が混在し、既存の翻訳器を置き換える根拠には不足している。

## 変更した処理と比較条件

[事前条件](paired-matcher-v1-protocol.md)に従い、原文とその言語の概念定義を固定MiniLMの二列入力へ渡した。tokenizerのsequence IDと文字位置を使い、原文内の対象範囲と定義の内容トークンを別々に平均する。指示文、生成、語別の補正規則は使っていない。元の3係数方式と異なり、対象表現にも候補定義との相互作用が含まれる。

共通ヘッドは対象q、定義d、その差の絶対値と要素積を入力し、コサインに最大±0.25の補正を加える。線形方式は1,537パラメーター、幅64の浅いMLPは98,433パラメーターで、候補数には依存しない。同じ形のヘッドを、原文と定義を別々に符号化した対照方式にも適用した。すべての方式で基盤モデルを固定している。

学習は既存の12概念・3,072範囲、開発は留保3概念・288範囲のままとした。今回、開発時の候補数を91へ増やし、確認時と揃えた。追加76概念は学習損失の正例・負例には使わないが、開発時の候補として選択へ関与するため、完全に未観察の概念とは呼ばない。

## 開発で選択した構成

epochと方式は開発日英平均だけで選択し、確認資料を使った調整は行わなかった。

| 符号化・ヘッド | 選択epoch | 日本語 | 英語 | 日英平均 |
| --- | ---: | ---: | ---: | ---: |
| 独立・線形 | 15 | 90.97% | 83.33% | 87.15% |
| 独立・MLP | 2 | 95.14% | 83.33% | 89.24% |
| 同時・線形 | 16 | 100% | 95.14% | 97.57% |
| 同時・MLP | 3 | 100% | 94.44% | 97.22% |

同時符号化・線形が選ばれた。ただし、開発の正例は鳥・助ける・公園の3概念に限られ、状態や動作を広く区別できた成績ではない。[選択記録](../reports/paired-matcher-v1/selection.json)と、同じディレクトリの4構成の全学習履歴を保存した。

## 新しい日英20組での確認

[v5](../data/definition-probe-v5.json)は、過去の資料と文の完全一致がない日英20既知概念・6未知概念の対である。各概念は観察済みのものを含み、同じ作成者による小規模資料である。正解の対象範囲を与えるため、下表は自然文全体の翻訳精度ではない。

| 方式 | 日本語 | 英語 | 日英とも正解 |
| --- | ---: | ---: | ---: |
| 既存MiniLM・3係数 | 13/20 | 13/20 | 13/20 |
| 独立・線形 | 15/20 | 15/20 | 12/20 |
| 独立・MLP | 15/20 | 12/20 | 11/20 |
| 同時・線形（開発で選択） | 14/20 | 14/20 | 11/20 |
| 同時・MLP | 14/20 | 13/20 | 11/20 |

同時・線形は日英の「使った／used」、英語の「taught」「message」、日本語の「必要だ」で既存方式の誤りを修正した。一方、英語の「heard」「spoke」と日本語の「学んだ」は、既存方式が正しかったものを誤った。「売った」は店、「開けた」は開いた状態など、関連概念や状態と動作の混同も残った。

独立・線形の方が新規資料では各言語の正解数が多かったが、この結果を使って選択を変更していない。開発での97.57%は、広い概念群での正しさを予測するには不十分だった。日英で同じ候補を返す組も既存18/20から同時・線形13/20へ減っており、各言語の正解数だけでは言語間の意味一致を評価できない。[全構成の集計](../reports/paired-matcher-v1/v5-evaluation.json)

未知6概念の日英12範囲には、全方式が既知候補を返した。借りるを渡す出来事へ、比喩的な「open」を開いた状態へ対応させるなど、未知判定は成立していない。全文は未確定のままであり、既知候補を選ぶスコアを確信度として使用していない。

## 過去の資料と予測範囲での回帰

観察済みv4では、同時・線形が日本語16/24・英語16/24、既存3係数方式が16/24・17/24だった。新規v5だけでなく、前回資料でも安定した改善は確認できなかった。[v4の集計](../reports/paired-matcher-v1/v4-evaluation.json)

さらに、以前の32文で保存した出来事・句範囲・役割logitを固定し、選択した同時・線形の概念スコアだけを入れ替えた。ここでは正解範囲を与えていない。

書く能動文と聞く文が改善し、飲む受動文が悪化した。飲む述語を洗う出来事へ対応させたが、型の制約には適合していた。未知のロボットを名前付き人物へ対応させる例もあり、必要な名前が未抽出という不整合を1件記録した。[32文の評価](../reports/paired-matcher-v1/joint-evaluation.json)

## 実装の検証と限界

全418テストが通過した。二列に同じ文字位置があっても混合しないこと、複数の対象範囲で同じ原文・定義のforwardを共有すること、候補を追加・並べ替えしてもヘッドの既存候補のスコアが保たれること、過長入力を切断せず拒否することを検査した。

4構成すべてを固定特徴から再学習し、選択epoch・全履歴・重みが完全一致した。v4とv5の112範囲で4構成の予測・集計を再計算し、32文の同時選択とその評価集計も再現した。同じ4組の特徴抽出は反復一致し、モデルを直接forwardした値からの抽出とも完全一致した。基盤モデルの重み固定・evalを確認し、生成等の禁止経路5種の呼出しは全て0回だった。[再現検査](../reports/paired-matcher-v1/verification.json)

二列入力は計算負担が大きい。学習では33,756組、開発では24,115組の原文・定義を符号化した。重複する原文・定義を共有しても、候補数に比例して基盤モデルの計算が増える。今回の最大入力長は128、実行環境はPython 3.12.10・PyTorch 2.13.0 CPU・float32・eager・8スレッドである。[条件とハッシュ](../reports/paired-matcher-v1/run.json)に記録した。

```powershell
artifacts/kwja-venv/Scripts/python.exe -m scripts.probe_paired_matcher
artifacts/kwja-venv/Scripts/python.exe -m scripts.probe_paired_matcher --verify-only
```

固定MiniLMのキャッシュと既存の選択資料・32文の生出力が必要で、出力先は上書きしない。特徴と重みはGit管理外の`artifacts/paired-matcher-v1`へ保存した。

今回の方式は研究用として保持する。状態がほぼ一種類に限られる学習資料と、3概念だけの開発資料は、候補数を91へ揃えても残る制約である。次は語彙に依存しない判定を維持しながら、関係する物体・述語・状態を区別する教師資料と開発区分を広げる必要がある。否定・時間・数量等を含む全文の意味構造一致率95%、広い自然文への対応、文字数の課題はいずれも未解決である。
