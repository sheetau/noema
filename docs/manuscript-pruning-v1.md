# 全ての文を保った宣言の整理

開発用の草案には、以前の読み方や接続方法の定義が履歴として残っている。全ての文と、原文との対応表に載っている定義を保持し、それらのいずれからも使われない宣言を取り除いた。新しい内容の記述や意味の短縮は行っていない。

| 草案 | 宣言数の変化 | 同じ短縮記法での文字数 | 削減率 | 保持した文 |
| --- | ---: | ---: | ---: | ---: |
| カント | 2,184 → 2,038 | 349,534 → 319,391 | 8.62% | 22 / 22 |
| アインシュタイン | 1,665 → 1,498 | 281,117 → 249,521 | 11.24% | 174 / 174 |

この文字数は定義を含む草案文書全体である。自然言語の一文を訳した場合の長さや、原文に対する圧縮率ではない。原文の未記述箇所も残るため、これを全文完成と扱わない。

## 保持するもの

解析器で元文書全体を検査した後、全ての文と追加ルートから参照をたどる。引用内、引用の構成、関数参照、列の集計、仮定の内側にある参照も対象にする。使われない定義に不正があっても、削除で隠して通さない。

文からの参照だけで選ぶと、過去の原文対応表が参照する定義も削除される。そこで対応記録を固定したスナップショットに保存し、各記録の出典と参照名を照合した。入力に存在するカント981記号、アインシュタイン634記号を追加ルートとして残した。過去の候補も含む保守的な保存であり、最小の定義集合ではない。

記号名、定義本体、文の順序と重複、束縛範囲、引用の階数は変更しない。同じ本体を持つ二つの名前も、引用した記述としては別物になり得るため統合しない。追加ルートを指定すれば、現在の文から使われていない再利用用の定義も保持できる。

カントでは657個、アインシュタインでは615個の原始関係が残る。それらの名前を保持しただけで、その概念を説明し終えたとは数えない。カントの14項目の未達一覧と8引数のひな形はそのまま残す。アインシュタインの意味基盤は保持した宣言へ絞り、未解決事項は全て引き継いだ。

アインシュタインの対応記録には、今回の入力文書に存在しない143記号もあった。整理で削除したものとは区別し、別草案に残る未統合候補として一覧に記録した。全草案の統合や、集計済みの対応範囲を一文書に全て収録したことは保証しない。

## 使用と検査

版0.16の引用構成を含む文書にも使える明示的なコマンドを追加した。入力の版は変更せず、出力先は未作成のパスを指定する。

```powershell
python -X utf8 -m noema.closed_document -i examples/v016/kant-policy-revision.noema -o artifacts/kant-reading.noema --manifest artifacts/kant-reading.json
python -X utf8 -m noema.closed_document -i examples/v016/kant-policy-revision.noema -o artifacts/kant-library.noema --root ryy --root ryz
python -X utf8 -m pytest -q tests/test_closed_document.py
python -X utf8 -m scripts.check_manuscript_pruning --verify-only
```

後者の抽出コマンドも全ての文を保存し、それに追加して指定した定義を残す。コマンド単体は原文対応表を自動で読まない。今回の保存済み文書は `scripts.compose_manuscript_pruning` が固定した対応記録を追加ルートに使って作成する。解析時に辞書やモデルを呼び出す処理はない。

[カントの整理済み草案](../examples/v016/kant-pruned-v1.noema)と[アインシュタインの整理済み草案](../examples/v014/einstein-pruned-v1.noema)は、そのまま各版で解析できる。[検査証明書](../data/manuscript-pruning-v1.json)には、各文と保持宣言の構文木ハッシュ、残した名前と削除した名前を記録した。証明書の検査では元文書から依存先を再計算するため、文の削除や証明書の改変を検出できる。

構文木の保存と、引用を含む有限モデルでの評価一致を検査する。原文とNoemaの意味一致は別の検証であり、この整理では意味確認済み区間と原文の対応範囲を増やさない。元の公開定義を外部から参照する利用者は、元文書か追加ルート指定を使う。評価器へ渡す原始関係の解釈も、整理後に残る宣言集合へ合わせる必要がある。
