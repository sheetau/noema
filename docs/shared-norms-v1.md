# 許可・義務と反事実の共通規約

## 再利用する定義と不足していた関係

許可と義務には、既存の `described-norms` の5定義を使う。出所・本人・役割・活動・実行記述・極性・評価状況を保持し、積極的な許可、反対要求の不在、要求の衝突、許可と要求の衝突、未履行を区別する。反事実には、[反事実の差し控え](counterfactual-withholding-v1.md)の `rqrs` を再利用する。この6定義は名前だけを一貫して変え、本体を保存する。

共通化に際して不足していたのは、要求・許可そのものの取得、履行と自由選択、規範と適用理由の結合、比較候補の選択規約、候補選択の視点と根拠である。これらを量化・関数・型付き引用から構成し、計21定義の[共通モジュール](../examples/v016/shared-norms-v1.noema)にした。文ごとの基本関係や文法演算子は追加していない。[公開契約](../data/shared-norms-basis-v1.json)に、各引数の型・役割・解釈条件と旧名の対応を記録する。

## 許可・義務・履行

規範の極性が真なら、記述された活動の成立が対象となり、偽なら不成立が対象となる。要求と積極的な許可は別の入力である。次の判定では、出所から評価状況までの七項目を同じまま保つ。

| 定義 | 条件 |
| --- | --- |
| `normrequired` | 指定極性への要求がある |
| `normpermitted` | 指定極性への積極的な許可がある |
| `normforbidden` | 反対極性への要求がある |
| `notforbidden` | 反対極性への要求がない |
| `permissionclear` | 指定極性を許可し、反対極性を要求しない |
| `demandconflict` | 成立と不成立の両方を要求する |
| `permissionconflict` | 指定極性を許可し、反対極性を要求する |
| `normoptional` | 成立・不成立の両方を許可し、どちらも要求しない |
| `normfulfilled` | 指定極性を要求し、実際の状態がそれに一致する |
| `normviolated` | 指定極性を要求し、実際の状態がそれに一致しない |

`normfulfilled` と `normviolated` だけが、対象の行為記述を実行して状態を調べる。他の判定は記述の同一性を保持したまま規範関係を参照する。同じ真偽を持つ二つの記述に同じ許可を移したり、実行できることから許可を補ったりしない。要求の不在と許可の不在も別々に表せる。要求そのものが不明なら、実行器は未知の入力として拒否する。

規範の根拠を明示する場合は `normwitness` を使う。同じ規範がその出所・状況で採用され、本人・役割に適用され、その規範と理由が同じ活動・記述・極性を支えることを要求する。`groundedrule` は、この条件を満たす規範と理由の組が存在するという関係を返す。この関数を要求用と許可用に別々に構成して、上の判定へ渡せる。別の規範から採用・適用・根拠を寄せ集めることはできない。

採用と適用の入力には、どの規範体系を使い、例外や優先順位をどう扱ったかを明記する。衝突を記述することは、その解決を認定することではない。これらの定義から、規範の普遍的正当性、制裁、本人の責任、要求があれば実行可能であるという原則は導かない。

## 比較候補と反事実

`conditionalvalid` は、選択した比較候補が非空で、そのすべてが前提を満たすことを要求する。`conditionalall` はその全候補での帰結、`conditionalmight` は少なくとも一つの候補での帰結を調べる。前提と帰結を別々の候補で満たしても成立しない。

保存した `contraryconditional` は、現実では前提が偽であるという条件も加える。この条件を伴わない仮定には `conditionalall` を使う。どちらも現実の帰結を肯定も否定もしない。未知の前提を偽と扱ったり、前提を満たす候補がないことを空虚な成功と扱ったりしない。ここでは「前提不能なら条件文を真とする」という読みを採っていない。

比較対象の範囲と優先関係を明示する場合は `comparisonbest` を使う。同じ現実状況の下で、前提を満たす候補のうち、それより優先される候補がないものをすべて選ぶ。同程度の候補や比較不能な候補を一つへ絞らず、帰結が真になる候補だけを後から選び直さない。

`comparisonordered` は、この前提適合範囲で優先関係が非反射的かつ推移的であることを検査する。`orderedconditional` と `orderedmight` は順序検査と最良候補での全称・存在判定を結び付ける。不正な順序なら両方とも成立しない。順序が妥当でも、無限に改善する候補列などで最良候補がなければ成立しない。有限検査から無限領域の最良候補の存在を保証することはしない。

範囲と優先関係の選定には、何を背景として固定し、何の違いを重く扱うかという解釈が残る。数値距離や唯一の最類似状況を言語側で勝手に補わない。`counterfactualsupported` では、視点の人物・前提の閉じた記述・理由・現実状況・各比較候補を根拠関係へ結び付ける。前提として実行する関数は、その同じ引用記述から取得する。根拠の十分性は明示した規約の入力であり、自動証明ではない。因果関係を述べる場合には、これとは別の関係を追加する。

## 二題材への適用と検証範囲

[Native例文](../examples/v016/norms-counterfactual-v1.noema)は、本の貸出と装置の起動という架空の二題材を使う。貸出には積極的な許可があり、要求はない。起動には要求があり、実際には起動していない。実行方法の有無は既存の `methodpossible` で別に調べる。起動の要求は、同じ規範と理由を使う `groundedrule` からも構成する。

条件文の例では、本の提供があった比較候補を二つ残し、一方だけで受領が成立する。全候補での帰結は偽、少なくとも一候補での帰結は真となる。装置では、スイッチを入れた二つの比較候補の両方で稼働する。いずれも現実では前提が偽であり、比較候補での成立から現実の受領・稼働を補わない。例の基本関係は検査用の明示的な解釈であり、現実の貸出制度や装置の仕様を認定するものではない。

[検査報告](../reports/shared-norms-v1.json)には、二題材での規範128モデル、比較候補と前提・帰結の256モデル、二状況での候補範囲と優先関係256モデルを記録する。規範根拠の9項目と比較根拠の5項目は、それぞれ一項目ずつ変える16件の結合診断を行う。これは全組合せの証明ではない。三候補での非推移性、同程度の候補、循環、不正な候補、引用の同一性、未知の入力、規範の証人の取り違えは別のテストで検査する。

```powershell
python -X utf8 -m noema.meaning_catalog explain --basis data/shared-norms-basis-v1.json --symbol normoptional
python -X utf8 -m scripts.project_work check --module scripts.check_shared_norms --tests tests/test_shared_norms.py --prepare --verify reports/shared-norms-v1.json
```

二作品の本文・意味判断と旧規範定義は変更しない。今回の規約は、許可・義務・反事実について明示した読みを共通化するものであり、全用法や自動的な規範推論を網羅する証明ではない。この21語の円文字登録、学習用の説明と第三者読解は別途必要である。
