# モデル内の文字位置と原文の位置

自然言語の抽出結果は、原文のどの範囲を根拠にしたかを保持する。モデルのトークナイザーが文字を正規化すると、文字数が変わることがある。その場合にも、画面や意味解析の範囲を原文の位置で扱えるようにする。

| 原文 | 文字モデル内の表記 | 原文範囲とモデル範囲 |
|---|---|---|
| `…` | `...` | 原文1文字とモデル3文字を対応付ける |
| `e`＋結合アキュート | `é` | 原文2文字とモデル1文字を対応付ける |
| `㍍` | `メートル` | 原文1文字とモデル4文字を対応付ける |

`normalized_ranges`はUnicodeのNFKC正規化を使い、モデルの各文字に原文の範囲を割り当てる。正規化で範囲が重なる出力文字は一つのまとまりにする。モデルの分割予測はその先頭へ戻し、展開・合成された範囲の内部で原文を切らない。原文は書き換えず、最終的な語の表層を連結すると元の入力と完全に一致することを検査する。

文字モデルの語彙と重みは既存のものを使う。`[MASK]`のような原文も、文字モデルには文字として入力する。モデル自身が必要とするCLS・SEPは、本文と区別して付加する。語の意味を推定するための文字別の補正表は追加しない。

後段の語トークナイザーも、正規化で一語を空出力にする場合がある。たとえば全角空白が単独の語になった場合である。`PreservingWordTokenizer`は消えた語番号を検出し、モデル既定の未知語トークンを一つ割り当てる。元の語の文字列と位置は維持する。既に符号化できていた語のトークン列が変わらないことも検査する。

研究用の日本語解析では、次のAPIを使う。旧`JapanesePAS`は過去の実験を再現するために保持する。

```python
from noema.japanese_pas_aligned import AlignedJapanesePAS

parser = AlignedJapanesePAS()
prediction, vectors = parser.analyze("太郎は待った…花子は来た。", return_features=True)
```

`prediction["text"]`は原文、`tokens`の`start`・`end`は原文のUnicodeコードポイント位置である。`vectors`の行は各語に対応する。モデル内の正規化方式、Unicode版、位置対応のコード版は`parser.metadata`へ保存する。文字数・トークン数の上限も維持し、範囲を保てない入力を黙って切り詰めない。

この部品は原文位置を保持するための処理である。語義・役割・参照・数量などの判定精度は、後段で別に測定する。
